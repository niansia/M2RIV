# RFC 0015: MCR 0.4 evidence identity, native evidence, and target root

- Status: Accepted
- Date: 2026-08-29
- Contract impact: Breaking pre-1.0 MCR envelope and identity change

## Problem

The previous envelope used one stable `id` for evidence and could therefore give
opposite PASS/BLOCK decisions the same report identity. A single completeness
boolean also blurred three different facts: whether bundle components were
rehashed, whether evidence bodies were retained, and whether metrics could be
recomputed. Target GPU evidence retained Polygraphy, ONNX, and engine files but
did not bind every byte into one portable root. Finally, the `m2riv:` wire
namespace coupled the protocol to a provisional product name.

## Decision

MCR 0.4 adopts:

1. `mcr:sha256:` content IDs and `mcr:<namespace>:v1` domain separation;
2. replay-stable `evidence_id`, decision-bound report `id`, and exact `run_id`;
3. separate bundle completeness, evidence-body coverage, and metric
   recomputability results;
4. `ToolNativeEvidence`, `SnapshotArtifactManifest`, and
   `BuildProvenanceEvidence` contracts;
5. comparator-native evidence whose structured verdict and native exit code must
   agree;
6. `TargetEvidenceManifest`, covering every retained target file and strict MCR;
7. fixed PASS/WARN/BLOCK/ERROR vectors and mandatory negative fixtures;
8. an MCR-owned media type and canonical `mcr-report.json` filename.

## Identity rules

`evidence_id` covers stable snapshots, plan, stable metrics, evidence links, and
supplemental evidence references. Report `id` covers the evidence ID, plan ID, and
complete decision. `run_id` covers the exact execution including timestamp,
runtime metrics, cache provenance, limitations, evidence, and decision. Contract
locators are excluded only where their schema explicitly defines a retained byte
digest as the portable identity.

## Security and trust

All new verifiers perform bounded, no-follow local reads and recompute digests.
The target root rejects changed, missing, or unlisted retained files. These are
content-integrity properties, not keyed authentication or producer identity.
Authenticity remains external through trusted CI, attestations, signatures, or a
future protocol extension.

## Compatibility

This is deliberately breaking before public 1.0. Current tooling rejects legacy
1.3 bundles with a migration message. Implementations must regenerate bundles;
string replacement cannot produce valid new identities. The full procedure is
documented in `docs/mcr-0.4-migration.md`.

## Acceptance tests

- identical evidence plus opposite verdicts share `evidence_id` but not `id` or
  `run_id`;
- tampered native output invalidates the linked bundle;
- build-parameter or calibration-cohort changes alter build provenance identity;
- missing, changed, or unlisted target files invalidate the target root;
- ERROR is preserved and non-authorizing;
- all negative conformance fixtures are rejected;
- Python, Node, and Rust agree on RFC 0012 vectors and Python/Rust report identity.
